Семена Знаний

Локальная инструкция по установке, запуску, резервному копированию и безопасной передаче Telegram-магазина.

1. Что входит в проект

  • Telegram-бот на Aiogram с админ-панелью, заказами, поддержкой и каталогом.
  • Telegram Mini App на Flask: каталог, корзина, промокоды, оформление заказа и WebApp-аутентификация.
  • SQLite-база с миграциями, persistent-корзинами и хранением FSM-состояний.
  • Оплата картой/СБП с ручным подтверждением, Telegram Stars и ЮKassa с hosted checkout.

В RUN_MODE=webhook запускается один общий процесс main.py: он обслуживает Telegram webhook и Flask Mini App/API на одном HOST:PORT. В RUN_MODE=polling бот и Mini App запускаются разными процессами и должны использовать разные порты.

2. Требования

  • Windows, Linux или macOS.
  • Python 3.11 или новее.
  • Публичный HTTPS-домен для Mini App в production.
  • Telegram-бот, созданный через BotFather.
python -m venv .venv
.venv\Scripts\python.exe -m pip install --upgrade pip
.venv\Scripts\python.exe -m pip install -r requirements.txt

На Linux/macOS вместо .venv\Scripts\python.exe используйте .venv/bin/python.

WEBAPP_URLПубличный HTTPS-адрес Mini App. Бот передаёт его в кнопке открытия магазина.
OWNER_TELEGRAM_IDЕдинственный неизменяемый Telegram ID владельца. Владелец назначает менеджеров и кладовщиков в защищённом разделе Operations Mini App.

DATABASE_PATHОбязательный абсолютный путь к общей SQLite-базе. Если файла нет, приложение создаст его и применит схему.
RUN_MODEРабочий переключатель: polling запускает получение updates через Telegram API; webhook запускает aiohttp webhook listener.
WEBHOOK_URLОбязательный публичный HTTPS URL вида https://домен/webhook только для режима webhook.

HOST / PORTАдрес и порт HTTP-сервера текущего запуска. В webhook режиме это общий listener для Telegram и Mini App; standalone Flask также использует эти значения.
YOOKASSA_SHOP_IDИдентификатор магазина из личного кабинета ЮKassa. Нужен только серверу для создания и проверки платежей.
YOOKASSA_SECRET_KEYСекрет API ЮKassa. Хранится только в .env или secret store, не вводится в Telegram, не попадает в SQLite, ответы API, логи или Git.
YOOKASSA_RETURN_URLПубличный HTTPS-адрес /payments/yookassa/return. Это только возврат в Mini App после оплаты, а не подтверждение платежа.
LOG_FORMAT / LOG_LEVELjson включает безопасные структурированные события в stdout; журналы не содержат реквизиты, payload webhook, initData или секреты.
REPORT_TIMEZONEЧасовой пояс периодов CSV-продаж, например Europe/Moscow.
BACKUP_DIRАбсолютная защищённая папка вне проекта и папки БД. Обязательна только для команды online backup.
BACKUP_DAILY_RETENTION / BACKUP_MONTHLY_RETENTION / BACKUP_INTERVAL_SECONDSЧисло daily/monthly копий и интервал schedule. Backup использует SQLite online backup, integrity/foreign-key/schema проверку и lease, поэтому polling и webhook процессы не создают одну копию параллельно.

DELIVERY_ENCRYPTION_KEYS_JSONJSON keyring base64url-ключей AES-256-GCM. Только для .env или secret store; не передаётся в Telegram, SQLite, API, логи или Git.

Не сохраняйте token в исходниках, URL изображений, логах, скриншотах или Git-коммитах. При любом раскрытии token немедленно отзовите его через BotFather и выпустите новый.

4. Первый запуск

Webhook: единый запуск бота и Mini App

# В .env:
RUN_MODE=webhook
PORT=8081

# Затем:
.venv\Scripts\python.exe main.py

Один процесс обслуживает Mini App/API и POST /webhook на HOST:PORT. Внешний HTTPS reverse proxy должен направлять все пути на этот процесс.

Polling: два процесса

# В .env перед запуском Mini App:
RUN_MODE=polling
PORT=8080

# Окно 1:
.venv\Scripts\python.exe server.py

# Окно 2:
.venv\Scripts\python.exe main.py

При первом запуске SQLite создаст файл базы и таблицы автоматически. Для production Flask не должен запускаться с debug=True; разместите его за HTTPS reverse proxy или WSGI-сервером и проверьте, что proxy передаёт заголовок X-Telegram-Init-Data.

4.5. White-label: рабочий порядок

White-label платформа разделена на control plane и изолированные runtime каждого магазина. У каждого клиента собственные SQLite-база, папка media, резервные копии, домен, bot token и платёжные credentials. Один runtime-процесс обслуживает только один магазин.

Платформенный администратор

  1. Откройте Platform Console через платформенного Telegram-бота и создайте черновик магазина: название, slug, Telegram ID владельца и тариф Старт, Бизнес или Pro.
  2. В managed-режиме вставьте Bot Token и Webhook Secret один раз в password-поля Console. Console передаёт их только локальному one-way sealer и сохраняет envelope ciphertext; значение не возвращается в API, audit или интерфейс. Не используйте для новых managed tenant env:-ссылки, .env, SQLite, Telegram или Git для этих секретов.
  3. Нажмите «Подготовить runtime»: Console создаёт только durable job. Root-only controller создаёт отдельные app.sqlite, media, backups, Linux UID, подписанный manifest, systemd unit и canonical Caddy route; HTTP-запрос Console не выполняет root-операции.
  4. Managed mode требует одноразового root bootstrap только на новом disposable VPS: после размещения проверенного source release по пути /opt/bookapp/releases/current выполните sudo bash deploy/bootstrap-managed-platform.sh. Скрипт создаёт release-local .venv из Linux/Python 3.12 hash lock, затем создаёт отдельные service identities platform-console, platform-controller, platform-control, root-only host-operations helper, закрытые каталоги, controller keys, шаблон bookapp-tenant@.service и import Caddy site fragments. Он намеренно не включает службы, не записывает bot token и не меняет основной Caddyfile. Console и controller разделяют только group-scoped control SQLite directory; tenant никогда не получает доступ к control DB.
  5. Не включайте controller для уже работающего legacy tenant автоматически. Сначала проверьте bootstrap и ACL на disposable VPS с новым test-tenant; для legacy tenant нужен отдельный migration/adoption workflow.
  6. В managed bootstrap запускайте HTTP Console как bookapp-console.service от UID platform-console, platform controller — как bookapp-controller.service от UID platform-controller, а root-only bookapp-host-operations.service выполняет только UUID-bound account/storage/systemd/Caddy операции по локальному socket protocol. Console и platform bot получают общий platform bot token только через systemd credential platform_bot_token; controller получает KEK/signing key только через собственные systemd credentials. Managed process игнорирует shared .env и ambient PLATFORM_BOT_TOKEN. Для бота обязательно задайте в root-owned platform-bot.env PLATFORM_CONSOLE_URL=https://platform.example.ru: это публичный HTTPS origin Console, а не localhost и не tenant domain.
  7. В BotFather задайте этот же PLATFORM_CONSOLE_URL как Menu Button платформенного бота. Запускайте только один polling process для этого token; не включайте ему Telegram webhook одновременно. Если VPS не имеет прямого доступа к Telegram, укажите PLATFORM_BOT_PROXY_URL=http://login:password@ip:port только в root-owned platform-bot.env. Proxy используется только платформенным ботом; не направляет Console, Caddy или tenant runtime через себя. Не публикуйте этот URL: в нём содержатся учётные данные proxy.
  8. Откройте Console кнопкой из личного чата с платформенным ботом. Обычный браузер намеренно не авторизуется: защищённые API без Telegram initData вернут 401, а неадминистратор получит 403.
  9. Для test-магазина создайте отдельного Telegram-бота и уникальный test-* slug. Введите две обязательные secret values и, при необходимости, необязательный bot_proxy_url формата http://login:password@ip:port; он шифруется, materialize только этому runtime и не попадает в shared .env. Поставьте provisioning в очередь, дождитесь статуса running, подтвердите владельца через canonical /setup и поставьте активацию в очередь. Это не то же самое, что PLATFORM_BOT_PROXY_URL платформенного бота и не global HTTP proxy. YooKassa и delivery keys добавляются отдельным этапом.
  10. Выбор тарифа в Console сразу показывает его стандартные модули и лимиты, но сохраняется только кнопкой «Сохранить тариф и модули». Изменённые вручную checkbox становятся feature overrides.
  11. Custom domain сначала pending. После настройки DNS нажмите «Подтвердить DNS и routing»; в managed mode controller автоматически применит verified hosts, а при отключении автоматически удалит hostname из route и signed manifest. Без подтверждения домен не маршрутизируется. Не добавляйте generated routes в Caddyfile текущего legacy VPS.
  12. HTTP Platform Console требует PLATFORM_DATABASE_PATH, PLATFORM_TENANT_DATA_ROOT и PLATFORM_TENANT_BACKUP_ROOT; ей не нужен фиктивный legacy DATABASE_PATH. Standalone legacy runtime использует DATABASE_PATH, а managed tenant worker получает tenant-local путь автоматически через launcher.
  13. Если provisioning показывает migration_failed, после исправления прав/настроек просто нажмите «Подготовить runtime» повторно: инициализация tenant-private папок и БД идемпотентна. Не удаляйте вручную tenant БД и не меняйте lifecycle через SQLite.
  14. Сообщение Python-dotenv could not parse statement starting at line N означает повреждённую строку N либо незакрытую кавычку строкой выше в .env. Откройте файл, оставьте только строки KEY=value или комментарии, завершите кавычки и держите JSON одной валидной строкой. Не отправляйте .env в чат; после исправления перезапустите Platform Console.
  15. Для disposable host main Caddyfile должен top-level импортировать /etc/caddy/bookapp-tenants.import; controller публикует только full Caddy site fragments из verified canonical host и UUID-derived Unix socket. Используйте отдельные test DNS records и сертификаты. Не добавляйте import или generated routes в Caddyfile текущего legacy VPS.
  16. После того как владелец подтвердит магазин в /setup, нажмите «Активировать магазин» в Platform Console. До активации публичная витрина недоступна, а canonical host допускает только owner onboarding.

Владелец магазина

  1. Откройте /setup
  2. Тариф, лимиты, включённые модули, домен, lifecycle, bot и платёжные секреты меняет только платформенный администратор.
  3. Добавляйте книгу через поддерживаемый мастер: название, автор, описание, цена, остаток, категория, затем Telegram-фото обложки и страниц.

Медиа принимаются только как Telegram-фото. Бот локально обрабатывает их в tenant-private WebP варианты и Mini App получает только opaque URL вида /media/books/<asset-id>/display. Ссылки на изображения не принимаются. Старые внешние изображения могут отображаться только временно до замены загруженными фото; Telegram/Bot API file URL не выдаются клиенту.

БизнесСтарт + сотрудники, склад, импорт, аналитика1 000 книг, 5 сотрудников, 2 импорта в сутки

Проверка перед передачей

  • Проверьте, что BOOK_MEDIA_ROOT — абсолютная tenant-private папка вне репозитория и public static tree; в tenant runtime она задаётся provisioning автоматически.
  • Откройте витрину на verified host, добавьте обложку и album страниц, затем проверьте карточку, модалку, замену и удаление фото.
  • В Operations убедитесь, что остатки загружаются без журнала, а движения появляются только после кнопки Журнал действий.
  • Проверьте checkout, tenant-local backup, lifecycle и отсутствие cross-tenant доступа для двух тестовых магазинов.

5. Настройка Telegram Mini App

  1. Разместите Mini App по адресу из WEBAPP_URL с действующим HTTPS-сертификатом.
  2. Укажите этот адрес для Web App у бота в BotFather.
  3. Откройте бота в Telegram, нажмите кнопку магазина и убедитесь, что каталог загружается.
  4. Добавьте товар в корзину, полностью закройте Mini App и откройте снова: корзина должна восстановиться для того же Telegram-пользователя.
  5. Проверьте под другой Telegram-учётной записью, что она не видит чужую корзину.

Корзина и checkout принимают пользователя только из серверно проверенного Telegram initData. Обычный браузер без Telegram не сможет сохранять серверную корзину или оформлять заказ.

6. Настройка оплаты

  1. Откройте в боте Админ-панель → Настройки оплаты. Там отдельно включаются реквизиты, Telegram Stars и ЮKassa; покупатель выбирает только доступный способ при checkout.
  2. Для ручной оплаты заполните хотя бы карту или СБП. Покупатель сообщает о переводе кнопкой в сообщении Telegram, после чего администратор проверяет поступление.
  3. Для Stars задайте курс и убедитесь, что товары соответствуют правилам Telegram для этого способа.
  4. Для ЮKassa создайте магазин и тестовый ключ в личном кабинете, поместите три переменные YOOKASSA_* в локальный secret store, перезапустите процесс и только затем включите метод в админ-панели.
  5. В личном кабинете ЮKassa зарегистрируйте публичный HTTPS endpoint POST /webhooks/yookassa и события успешной оплаты и отмены платежа.

Сначала в ЮKassa сохраняется локальная попытка с idempotency key, затем создаётся hosted redirect. Повторный запрос не создаёт второй заказ или второе списание. Статус меняется на «оплачен» только после webhook и независимой проверки платежа через API ЮKassa; return URL ничего не подтверждает.

Для прямого доступа приложение проверяет адрес отправителя webhook. Если перед ним стоит reverse proxy, ограничьте путь /webhooks/yookassa официальными IP-адресами ЮKassa на границе сети и не передавайте произвольный X-Forwarded-For как доверенный адрес клиента.

7. Доставка и самовывоз

Доступны три способа: СДЭК — пункт выдачи и Почта России — отделение по 500 ₽, а также самовывоз за 0 ₽. Расчёт тарифов, поиск отделений, печать ярлыков и автоматическая проверка статуса перевозчика не входят в текущую версию.

По умолчанию доставка выключена: это режим для цифровых книг. В managed tenant шифрование создаётся платформой автоматически при deployment; не добавляйте delivery keys в tenant .env. Если managed encryption временно недоступно, проверьте статус deployment/redeploy в Platform Console. Для standalone/legacy запуска настройте keyring ниже и перезапустите процессы, затем откройте Админ-панель → 🚚 Доставка.

  1. Для СДЭК покупатель указывает получателя, телефон, город и код либо адрес ПВЗ. Для Почты России — получателя, телефон, город и индекс либо адрес выбранного отделения.
  2. Самовывоз нельзя включить, пока администратор не задал адрес, график и инструкцию. Эти публичные условия фиксируются в созданном заказе и показываются покупателю в «Моих заказах».
  3. В карточке заказа нажмите Данные доставки. Данные покупателя для СДЭК/Почты России расшифровываются только по явному действию администратора и отправляются в личный Telegram-чат с protected content.
  4. После сборки для СДЭК введите трек из букв, цифр и дефиса; для Почты России — 14-значный номер отправления. Ссылки создаются сервером только на официальные страницы tracking, произвольные URL не принимаются.
  5. Самовывоз проходит этапы «Собран → Готов к выдаче → Выдан / доставлен» и не имеет трек-номера.
  6. После статуса «Выдан / доставлен» через 90 календарных дней зашифрованные данные покупателя удаляются. Статус, сумма, трек и состав заказа остаются для учёта.

Standalone/legacy: создание и ротация ключа

# Выполните локально один раз и сохраните результат только в secret store:
.venv\Scripts\python.exe -c "import base64, secrets; print(base64.urlsafe_b64encode(secrets.token_bytes(32)).decode().rstrip('='))"

# В .env (одна строка JSON, без опубликования ключа):
DELIVERY_ENCRYPTION_ACTIVE_KEY_ID=2026-09
DELIVERY_ENCRYPTION_KEYS_JSON={"2026-09":"результат_команды"}

Для ротации добавьте новый ключ в JSON, назначьте его DELIVERY_ENCRYPTION_ACTIVE_KEY_ID и перезапустите приложение. Старый ключ остаётся decrypt-only: не удаляйте его, пока все записи с ним не обезличены и не истёк срок хранения резервных копий. Неверный или отсутствующий keyring останавливает checkout доставки без сохранения адреса.

SQLite и её backup содержат зашифрованные данные доставки. Доступ к файлам БД, .env и резервным копиям должен быть только у service account и доверенных администраторов; не публикуйте их и не отправляйте в поддержку.

8. Администрирование каталога

  • Обычное удаление книги переносит её в архив и скрывает из магазина.
  • В управлении книгами можно выбрать несколько книг на разных страницах и одним действием перенести их в архив.
  • В архиве книгу можно восстановить.
  • Удалить навсегда можно только архивную книгу без исторических заказов. Для удаления нужен одноразовый код подтверждения.
  • Книги, присутствующие в заказах, остаются в архиве для сохранения бухгалтерской истории и выгрузок.

10. Резервная копия и восстановление

  1. Задайте абсолютный BACKUP_DIR на зашифрованном диске вне репозитория, static-папки и каталога SQLite; выдайте запись только service account.
  2. Создайте проверенную online-копию без остановки бота: .venv\Scripts\python.exe -m db.backups. Команда использует SQLite backup API, проверяет quick_check/foreign_key_check и завершится с ошибкой, если копия невалидна.
  3. При заданном BACKUP_DIR main.py запускает проверенный backup-loop; SQLite lease не даёт polling/webhook процессам создать одну копию параллельно. Внешний Планировщик заданий остаётся рекомендуемой независимой проверкой: .venv\Scripts\python.exe -m db.backups.
  4. Команда хранит 14 последних daily-копий и по одной копии за 3 предыдущих месяца. В админском Mini App отображается итог последнего запуска.
  5. Раз в квартал проверяйте восстановление: остановите все процессы, замените production-БД копией в отдельной тестовой среде, выполните PRAGMA integrity_check, откройте каталог и проверьте заказ.

Не публикуйте SQLite backup: в нём есть история заказов и сохранённые реквизиты ручной оплаты. Для аварийного raw-copy остановите все процессы; в WAL-режиме нельзя копировать только основной файл БД.

11. Передача проекта покупателю

  1. Передайте исходный код без .env, без SQLite production-базы и без папки .venv.

  3. Покупатель создаёт новую SQLite-базу через свой DATABASE_PATH либо получает отдельную согласованную копию данных.
